## 模型、工具与流程分别有什么问题

工具层存在直接错误证据：本会话 Computer Use 不可用，以及实际读取路径无法得到文件列表、系统截图失败。浏览器能操作Google和分享网页，不等于能操作独立客户端；浏览器截图成功也不证明系统截图可用。其他Agent在同机成功不能替代ZCode本会话的能力验证。

执行层出现了证据与结论不匹配：首个会话由2.24GB体积和片长估算1080p；通用“高清资源”文件名也不能证明分辨率。它一度称CLI没有分享文件列表命令，后续会话实际成功使用`share-detail`及子目录参数，说明能力发现与文档使用也影响效率。最新会话超出检索预算后仍追加核验。空内容树、截图失败后反复扩展底层诊断，说明已有停止规则没有形成有效约束。

版本需要区分：首个会话加载的历史文本和当前仓库规则不能混为一谈。后续版本已明确禁止CLI和网页登录下载，但仍出现重复诊断和长时间未提交任务。ZCode安装副本与仓库入口也存在文本差异，不能认为修改仓库会自动改变当前运行会话。

skill层最关键的问题是检查顺序：客户端能力属于下载前置条件，却在搜片、核验和转存以后才发现不可用。规则虽然有检索预算与恢复轮次，缺少靠前的能力门槛、客户端恢复总时限，以及对截图错误的审慎归因。继续堆叠更多坐标和异常说明，不能修复缺失的宿主能力。

## 本次仓库修改

1. 在搜片/转存之前验证当前会话的客户端观察与输入；已有资源不重复检索。
2. 自检通常90秒内完成；主动恢复最多两轮、3分钟。正常文件传输等待不受此限制。
3. 区分宿主能力不可用、空内容树和捕获失败，不承诺授权或重启必定生效；停止端口、TCC、临时截图器等无限扩展诊断。
4. 按实际截止时间收束Google检索，禁止超时后追加“快速复核”。
5. 明确体积不能证明分辨率，不通过整份转存未验证分享绕过核验；不删除任务登记来消除冲突。

这些是提示与流程层修正，没有新增客户端控制后端。审计修改完成后，已按用户要求通过安装器升级到`~/.zcode/skills/qfetch`，旧版本已备份，安装文件逐一与仓库核对一致。运行中的ZCode会话是否重新加载skill，仍须在该会话中验证。

## 后续如何验证是否有效

先在ZCode同一会话完成客户端能力验收：能看见文件列表、能确认一次无副作用输入或选择的变化。失败则修复宿主提供的能力，再验证；不能用搜片次数代替此验收。

能力通过后，先用有权访问的小文件验证“选择文件 → 指定目录 → 客户端出现任务 → 完成列表 → 本地落盘”；再用明确分享的GB级文件验证大文件流程；最后才加入Google发现，分开记录“分享已核验、转存成功、任务提交、最终完成”。记录首次任务提交耗时、无效重试次数和最终完成率；任何故障都应保留准确阶段。

若要比较模型，固定相同工具、权限、资源和skill版本，使用多次匹配任务对照。现有证据支持先修复宿主能力和失败收束，不支持“升级模型即可成功”的结论。本次没有端到端下载验收，不能声称下载成功率已提高。
